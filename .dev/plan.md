# 项目开发计划

本计划规定本次从零建设的分工、实施顺序、交付与验收。产品行为见 [产品设计](../docs/design.md)，通用开发、验证和授权见 [维护规范](../CONTRIBUTING.md)，实际状态见 [progress](progress.md)。

## 开发方案

### 人员与工具分工

| 角色 | 职责 |
|---|---|
| **Zcode / GLM** | 按已审定规格实现代码、测试和配套说明，完成自检与修复。 |
| **Codex / Astra** | 负责架构与科学设计、科学任务，以及 GLM 代码的技术验收。 |
| **人类专家** | 验收架构与科学成果，决定关卡放行及提交、保存、发布等操作授权。 |

上述分工适用于本次项目建设。[R24](#r24) 的项目与数据指南由 Codex / Astra 直接设计和制作，人类专家验收。

### 逐关实施与交接

1. 按 AGENTS 的入口阅读当前交接、对应关卡与相关设计，核对实际文件、Git 状态及所需成果。
2. 要求明确且开始条件满足时直接执行。实现安排与设计变更遵循 [开发工作约定](../CONTRIBUTING.md#开发工作约定)，其中的必要设计和影响评估由 Astra 负责。各关要求的先行设计、科学审定和实验批准须在使用前完成；整体计划通过不代表这些细节已获批准。
3. 代码任务先由 Astra 技术验收，再交人类专家审核；架构和科学成果由人类专家验收。科学任务先给出审定的规则与预期结果，后续代码任务据此验证。
4. 按 R00–R30 顺序逐关推进。每关完成验收及获准的 Git 交付后，才进入下一关；R01 起每关分别提交和推送，操作要求见 [Git 规范](../CONTRIBUTING.md#git-操作)。并行实施或合并关卡须经人类专家同意。
5. 暂停、完成工作或更换 Agent 前，更新 progress 的任务行和当前交接；重要决定按 [文档职责](../CONTRIBUTING.md#文档维护与防止漂移) 写回对应正文。

progress 的**任务总表**每关一行，记录验收状态、日期和简短结论。状态为“未开始、进行中、待审核、需修改、通过”；只有人类专家确认后才填写“通过”和验收日期。

**当前交接**固定为六项，每项事实只在对应栏目详细记录：

| 项目 | 写什么 |
|---|---|
| 任务与范围 | 当前任务及涉及的文件。 |
| 已完成 | 已交付的成果；产品能力可链接 README。 |
| 验证结果 | 实际命令、结果和未验证范围；较长命令用代码块或列表。 |
| 待解决 | 接续所需的未决问题、已知限制及待专家决定事项。 |
| 接续安排 | 下一步由谁做、开始条件及完成后交给谁。 |
| Git 与授权 | 具体获准内容和操作、实际完成情况、仍待批准的操作。 |

更新时替换当前内容，保留接续需要的结论和证据；实施转入验收时同步调整接续安排，Agent 用工具与模型标识。总表只保留摘要，详细验证与授权不在各栏目重述。提交与暂存以实际 Git 状态为准，不手工维护当前提交 SHA；没有明确批准依据不能视为获准。

同一工作目录可直接读取交接；换工作树或机器时先同步对应提交及必要的未提交改动，再核对文件与交接是否一致。含答案材料的存放和主仓交接范围见 [Gold 隐私要求](../../hvs-catalog-gold/README.md#操作与隐私)。

## 验证与实验安排

工程检查遵循 [验证要求](../CONTRIBUTING.md#验证要求)，各关另列需覆盖的场景。实验输入固定、指标、失败处理及最终评价独立性遵循 [评价设计](../docs/design.md#评价gold-与持续改进)。

真实提取实验须先完成 R07 的 Gold 审定和 R09 的评分核对。Astra 在各实验开工前提出材料、模型组合、重复轮次、通过条件及预算，取得对应范围批准。更换模型及按步骤选择模型的功能先用模拟服务验证。最终评价材料在 R08 准备与隔离、R28 标注、R29 评价。

模型 API 实验总额参考 1000 RMB；单次预计可能超过 100 RMB 时先提醒并等待确认。费用估算包含步骤、轮次和重试，实际型号、协议、路由及报价在准备实验时核实；未知用量或费用保留未知。小范围运行不自动扩大为 Full50 或更多组合。

引用错误来源的内容进入待审正式星表、同一决定重复生效或私有答案泄露，都属于必须修复的程序问题。科学指标具体要达到多少，在相应科学任务中确定。

## R00

**项目基础文档与系统目录设计**

**目标与范围：** 交付两仓的八份基础文档及 Git 忽略规则，明确总体设计、完整开发计划与维护要求。

**分工与开始条件：** Codex / Astra 编写，人类专家验收；工程骨架从 R01 开始。

**交付要求：** 八份文档的读者、正文职责与更新时机统一见 [文档职责表](../CONTRIBUTING.md#文档维护与防止漂移)。设计说明科学范围、模块职责、依赖与理由；31 关写明主要交付、依赖分工和验收标准。两仓忽略规则落实 [内容归属](../docs/design.md#内容进入哪里)。

**验收标准：** 八份文档及两仓忽略规则齐全，职责表要求的内容能在对应正文找到。文件与章节链接有效，规则一致；31 关所需成果来自更早关卡，progress 与计划对应。内部实现留给实现者，未决问题有明确处理责任。接手者无需读会话即可找到工作范围、验证结果、未决事项和接续安排。

Astra 逐项检查并说明限制，人类专家审核架构、科学范围、开发方案及全部关卡。链接检查通过仍须内容审核。本关只完成文档，不建立源码、环境、测试、数据库或正式数据。科学细则在 R03 审定，数据结构在 R04 实现，实验条件在对应任务确定。

**本关审阅与首次交付：** 以下约定仅适用于 R00。

**R00 直接在会话中审阅，不制作或更新 HTML，包括本关提交/推送前的说明。**

R00 获准交付时，两仓分别建立各自的第一个提交，不继承旧的提交历史。推送目标是各仓 origin 的 main 分支。首次覆盖远程前，须由人类专家批准具体提交和覆盖范围。推送前重新核对远程最新提交，并设置保护：只有远程仍是刚核对的版本时，才允许覆盖。

## R01

**文件架构与最小工程骨架**

**目标与交付：** 建立可以独立安装的最小 Python 包，提供命令行帮助和版本查询，以及安装与验证说明。

**分工与开始条件：** Zcode / GLM 实施，Codex / Astra 验收。开始前需完成 R00 的人类专家验收及获准 Git 交付。架构调整由 Astra 提出并交人类专家审定。

**关键要求：** 只建立当前需要的工程文件，依赖管理按维护规范执行；版本与发行范围分别遵循 [版本设计](../docs/design.md#保存恢复与版本) 和 [内容归属](../docs/design.md#内容进入哪里)。

**验收标准：** 在没有旧仓、Gold、密钥和本机专用路径的全新环境中，能安装构建产物，并从仓库外及独立子进程查询帮助和版本。实际支持的平台和安装步骤写入 README。

## R02

**LangGraph 持久化与恢复演示**

**目标与交付：** 用合成材料交付一个可暂停、保存决定并在程序重启后恢复的 LangGraph 演示，说明框架进度与业务数据的分工。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R01。框架不满足要求时由 Astra 提出设计调整，交人类专家验收。

**关键要求：** 演示验证 [保存与恢复规则](../docs/design.md#保存恢复与版本)，使用独立的合成演示空间。

**验收标准：** 实际终止进程并重新启动，能找回待办、复用已保存结果。相同决定只生效一次，冲突决定被拒绝。用模拟服务说明“收到响应但尚未保存就退出”可能造成重复调用及计费；演示不访问网络。

## R03

**科学规则、对象识别与资料补全规则**

**目标与交付：** 按 [科学规则的维护来源](../docs/design.md#科学规则的维护来源) 交付经人类专家审定的结构化规则材料、自动生成的阅读版，以及容易混淆的输入和预期结果；在本关确定具体子目录、文件格式和生成方式。

**分工与开始条件：** Astra 完成科学设计，人类专家逐项验收。开始前需完成 R00 的设计审定及 R02 的验收与获准 Git 交付。GLM 不自行决定科学规则。

**关键要求：** 明确论文与对象收录、当前贡献与引用、单个对象与群体、条件、单位、误差和缺失值、后续否定及证据要求。确定对象识别、外部资料范围、检索覆盖和自动通过或交专家的条件；提出评价目标。

**验收标准：** 阅读版由规则材料生成，规则、说明和例子一致，能避免无依据地把群体或条件结论归给单个对象。采用或修改规则有科学理由，未决问题不进入依赖它的实现。具体科学取值和阈值在本关审定，评分公式在 R09 实现前审定；科学边界遵循产品设计。

## R04

**核心数据格式与自动生成的格式说明**

**目标与交付：** 实现论文、来源包、贡献、名单、对象、外部资料、裁决和运行/发布记录，并从定义自动生成数据格式说明。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R03。科学表达问题由 Astra 设计并交人类专家验收后再编码。

**关键要求：** 表达 R03 审定的科学含义，保留原始表达与统一格式的对应关系。记录有版本、来源和可检查的引用；具体字段与保存格式在编码前确定。

**验收标准：** 合法记录保存后读回内容不变，生成说明与定义一致。版本未知、引用损坏或对象/论文对应错误会报错；缺失、区间和特殊值按规则表达，提取失败不被记成成功空结果。

## R05

**工作空间、运行记录与裁决基础**

**目标与交付：** 交付独立工作空间、配置与运行记录、备份恢复，以及创建和查询裁决待办、保存决定的共同接口。

**分工与开始条件：** Astra 先明确待办、决定保存和恢复接口，GLM 实施，Astra 验收。开始前需完成 R02、R04；记录含义采用 R03/R04 已审定的设计。

**关键要求：** 初始化保护已有资料，不同空间互不影响，数据修改完整保存。导入要求见 [内容归属](../docs/design.md#内容进入哪里)，执行锁与决定保存顺序见 [保存与恢复](../docs/design.md#保存恢复与版本)；网页与裁决命令在 R20 接入。

**验收标准：** 用模拟流程验证重复初始化、并发启动、保存中断和重启。待办、决定、论文与步骤对应正确；相同决定只生效一次，冲突或过期决定被拒绝。恢复备份后，材料、业务结果和框架进度保持一致，在仓库外也能运行。

## R06

**Gold 迁移、草稿检查与受控保存工具**

**目标与交付：** 用合成材料交付 Gold 迁移、逐项比较、草稿检查及获准保存工具，同时支持没有旧答案的全新草稿。

**分工与开始条件：** Astra 明确新旧格式的对应关系和允许进行的科学修改，人类专家验收科学含义；GLM 实现工具，Astra 验收。开始前需完成 R03–R05。

**关键要求：** 按 [Gold 标注、迁移与保存设计](../docs/design.md#评价gold-与持续改进) 实现工具。正式新标注由 Astra 根据原文制作草稿、人类专家审定。

**验收标准：** 既有答案迁移和全新草稿都能完成检查及模拟获准保存。输入损坏、版本不符、必要证据缺失、未批准或内容变化时拒绝保存；保存中断和重复操作不会留下半份答案或重复保存。回执读取失败时能先核对实际结果，旧输入始终只读。

## R07

**正式 Gold 迁移与科学审定**

**目标与交付：** 在获准范围内建立正式 Gold，保存材料清单、审定与来源依据，并准备供 R09 核对评分的固定参考预测。

**分工与开始条件：** Astra 使用 R06 已验收的工具执行迁移核查和科学复核，人类专家验收科学内容；GLM 修复已明确的工具问题并交 Astra 复验。开始前需完成 R06，并取得读取、迁移及保存 Gold 的具体授权。

**关键要求：** 先核对正式输入版本和审定依据，再逐项比较。科学修改须依据原文并由人类专家裁定；具体材料与保存内容另行批准。答案和详细分析留在 Gold 私有空间。

**验收标准：** 条目、身份、来源及科学内容能够逐项核对；含义未变的部分一致，修改有批准依据，未决项按规则保留。保存结果与批准内容一致，R09 能使用对应评价版本的参考预测。

## R08

**独立最终评价材料的准备与隔离**

**目标与交付：** 提前选出少量未用于开发的最终评价论文，交付固定清单、来源版本、选材理由和专家工作量估算。

**分工与开始条件：** Astra 选材并评估隔离条件，人类专家验收名单与工作量。开始前需完成 R03、R07，并取得材料获取授权。

**关键要求：** 核对材料是否参与过提取开发、提示或模型调整、案例积累。将选定材料单独保存并限制访问，正式标注安排在 R28。

**验收标准：** 能核查材料独立性和访问范围，已知限制明确，专家认可选材及工作量。样本规模在本关确定；开发期间不使用这些材料调试方法或配置。

## R09

**共享提取入口与独立评分基础**

**目标与交付：** 交付日常运行与评测共用的提取入口、方法与步骤约定，以及独立评分和报告功能。

**分工与开始条件：** Astra 完成指标定义、失败和部分结果计入分母的规则和科学通过条件，人类专家验收；GLM 实现，Astra 做技术及评分核对。开始前需完成 R04、R05、R07。

**关键要求：** 先审定指标公式、匹配规则、分母及通过条件。用模拟方法验证接口和名单到数值步骤的数据传递；实际提取在 R14–R16 完成。提取完成后单独读取 Gold 评分，答案不进入提取请求。

**验收标准：** 程序评分与手算样例及 R07 的参考预测核对一致，评价目标变化有说明。空预测、整篇失败和部分结果按规则计入分母，费用未知保留未知；评价输入变化可被发现，运行与评分入口实际可用。

## R10

**文献发现、导入与获取**

**目标与交付：** 交付按条件发现论文、按标识获取材料和导入本地文件的能力，保存元数据及来源版本。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R03、R05、R07。数据来源和检索范围由 Astra 设计、人类专家验收。

**关键要求：** 来源和检索范围按 R03 选择，具体服务在开工前核实。保留查询条件、时间和版本，处理分页、论文修订与重复输入；下载失败不能表示论文不相关，论文标识不能编造。

**验收标准：** 离线验证修订、重复、缺失全文、限流、无权限和无结果的处理。在批准的小范围内实际获取材料，确认满足检索要求，能回查标识、版本与来源。

## R11

**来源包、正文与表格解析**

**目标与交付：** 交付版本固定的论文来源包，解析正文及表格，使证据对应原文位置和正确对象。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R04、R10。来源解释中的科学歧义由人类专家裁定。

**关键要求：** 保留原始材料及文件、页、表、行列位置。开工前确定支持格式和解析方法，核对来源与许可；解析结果不能替代原文依据。

**验收标准：** 检查正文与表格的证据对应，尤其是 ECSV 异常列名（如 col_001）、YAML 头、多行和同名对象。无法匹配对象时不得默认使用第一行；解析失败、引用损坏和错误对象对应被发现。PDF 等格式只声明实测能力。

## R12

**模型接口与完整配置**

**目标与交付：** 交付可配置的模型调用接口，保存实际参数、响应、用量和失败状态。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R05、R09、R11。

**关键要求：** 按实际协议使用模型的完整配置，核对支持的参数；不强制不同模型采用同样设置，不擅自更换模型。对技术故障限制重试次数，日志与运行记录去除密钥。

**验收标准：** 模拟验证超时、限流、错误格式、截断、空响应、未知参数及用量缺失。能区分失败和无法确认调用是否完成的情况，未公开的默认值保留未知；真实服务调用另按范围授权。

## R13

**为各步骤选择模型、组合提示并保存运行配置**

**目标与交付：** 交付默认模型与按步骤指定模型的能力，保存实际完整提示及配置，供日常运行、恢复和评测共同使用。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R12、R03，并具备 R09 定义的方法与步骤接口。

**关键要求：** 共同科学要求、方法必需提示和模型补充提示职责清楚。关闭补充提示后科学要求仍完整；更换一步模型不改变其他步骤。恢复沿用固定输入，材料、规则、方法或配置变化后不能误用旧结果。

**验收标准：** 模拟验证多步骤模型组合、逐步用量及总费用。不存在的步骤会报错，不混用不同协议参数；恢复后模型和提示正确。真实组合在实验前选定，不自动遍历付费组合。

## R14

**统一名单格式与直接提取**

**目标与交付：** 实现 direct 名单方法，按规则直接提取对象、角色和证据，输出两种方法共用的名单格式。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R03、R04、R09、R11、R13。科学质量由 R17 的真实实验检验。

**关键要求：** 使用固定来源、规则和步骤配置，保留未决项，检查证据对应。方法不得按论文标识预置答案，格式修复有次数上限。

**验收标准：** 用模拟服务和 R03 样例检查贡献与引用、单个对象与群体、条件及后续否定。失败或截断不表示成功空名单。通过 R09 模拟步骤检查后续输入要求，R16 再验证与实际数值提取的连接。

## R15

**候选发现与逐项模型判定**

**目标与交付：** 实现 candidate_review 名单方法：先发现候选，再由模型逐项判定，保存每项证据、理由和进度。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R14、R02，以及 R05 的共同裁决接口。

**关键要求：** 发现和判定都能查看原材料。每个候选得到对应结果，尚未完成的候选不能自动排除；未决项交 R05 共同裁决接口，输出与 direct 共用后续流程。

**验收标准：** 发现重复或同名候选、无效证据、单项失败及分批结果错配。进程退出后能恢复部分结果，通过共同接口保存模拟决定并继续正确候选。候选遗漏单独检查，真实论文上的覆盖由 R17 评价。

## R16

**数值提取、自动检查与部分结果保存**

**目标与交付：** 交付完整论文提取流程，连接来源、两种名单方法、共同数值提取和自动检查，并提供日常运行入口。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R14、R15。

**关键要求：** 保留数值、误差或区间、单位、条件、对象及来源。区分技术失败、科学歧义和论文确实未报告内容；有效部分结果保留。逐篇保存进度，未决问题使用 R05 接口，不阻止其他可运行论文。

**验收标准：** 两种名单方法实际进入同一数值步骤，日常运行与评测使用相同配置和服务。模拟两篇论文，一篇等待裁决时另一篇能完成；重启后结果与待办正确，已保存结果可复用，决定只恢复对应论文。文献处理、R06 的 Gold 工具和评测入口均可执行。

## R17

**首轮真实提取实验与结构问题复查**

**目标与交付：** 交付首轮小范围真实提取实验，比较两种名单方法、科学质量、失败原因和多次运行稳定性。

**分工与开始条件：** Astra 设计并执行实验、分析结果，人类专家验收科学结论；GLM 修复范围和要求已明确的代码问题。开始前需完成 R07、R09–R16，并取得本次实验授权。

**关键要求：** 按 [实验安排](#验证与实验安排) 固定并批准本轮方案。比较方法遵循 [方法与模型选择](../docs/design.md#名单方法和模型选择)，保持模型配置组合及其他输入相同；先复查已知失败情况，保留全部轮次和费用。

**验收标准：** 按 [评价设计](../docs/design.md#评价gold-与持续改进) 报告各项指标、复验及结论范围，逐项对照通过条件。

## R18

**稳定对象身份与合并拆分**

**目标与交付：** 交付跨论文对象关联、稳定身份以及合并、拆分和更正能力，保留依据与原有论文贡献。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R03、R04、R05、R17。对象关联规则及科学分歧由 Astra 分析、人类专家验收。

**关键要求：** 按 R03 规则和 [科学边界](../docs/design.md#产品目标与科学边界) 使用标识、别名和位置提出关联建议；无法确定时通过 R05 保存待办，交专家裁决。

**验收标准：** 同名不同对象保持区分，改名不改变稳定 ID；合并拆分后贡献不丢失、不重复，旧链接和引用仍可解释。根据保存记录重建得到一致结果，未决关联可回查。

## R19

**来源明确的外部资料补全**

**目标与交付：** 从审定的外部来源补充允许使用的观测、标识和质量信息，保留匹配及来源依据。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R03、R18，并取得具体服务调用授权；科学字段与匹配解释由人类专家验收。

**关键要求：** 具体来源、字段和查询范围在开工前依据 R03 确定，可检查 SIMBAD 和 Gaia 等必要来源。保留查询、返回条目及版本，不覆盖论文值；计算与参数选择遵循 [科学边界](../docs/design.md#产品目标与科学边界)。

**验收标准：** 离线验证多匹配、无匹配、来源版本变化和服务故障；在批准范围内核对少量真实条目的字段、单位与出处。调用失败不表示数据库没有该对象，匹配不确定时保留待决状态。

## R20

**本地裁决网页、CLI 与恢复**

**目标与交付：** 将 R05 的共同裁决接口接入本地网页和命令行，让专家查看证据、保存决定并恢复任务。

**分工与开始条件：** Astra 设计操作流程及允许保存的内容，人类专家验收；GLM 实施，Astra 验证。开始前需完成 R02、R05、R16、R18、R19。

**关键要求：** 两种入口共用 [裁决功能](../docs/design.md#业务架构与依赖)，遵循 [保存与恢复规则](../docs/design.md#保存恢复与版本) 和 [本地用户流程](../docs/design.md#用户工作过程)；页面操作不自动公开数据。

**验收标准：** 真实浏览器验证待办与证据展示、刷新、关闭和重启。重复决定只生效一次，过期证据或规则对应的提交被拒绝，裁决后从正确步骤继续；网页和命令行行为一致，不同工作空间互不影响。

## R21

**裁决案例积累、复用与汇总**

**目标与交付：** 交付裁决案例的保存、查找、按条件复用和问题汇总，记录专家投入的时间。

**分工与开始条件：** Astra 设计复用规则并交人类专家验收，GLM 实施，Astra 验证。开始前需完成 R20。

**关键要求：** 按 [案例复用设计](../docs/design.md#评价gold-与持续改进) 审定适用条件并保留材料、规则、证据和原决定；产品不自行调用开发 Agent 修改代码或启动实验。

**验收标准：** 符合条件的案例可复用，条件变化后重新检查；复用引用原批准，不生成一次虚假的新批准。新增案例不改变当前评测，重复问题、待办和专家用时能够导出查看。

## R22

**正式星表候选与数据导出**

**目标与交付：** 从工作结果生成版本明确、来源可查的星表候选和下载表格，支持在已有星表上新增论文与修订记录。

**分工与开始条件：** Astra 确定哪些结果可以入库、导出内容如何表达，人类专家验收；GLM 实现，Astra 验证。开始前需完成 R18–R21。

**关键要求：** 按专家审定的入库和导出规则、[科学边界](../docs/design.md#产品目标与科学边界) 及 [增量修订与发布流程](../docs/design.md#用户工作过程) 准备候选。不同来源测量不能合成推荐值，正式保存须批准准确内容。

**验收标准：** 相同输入产生相同候选内容及哈希，贡献和引用不丢失、不重复；关键证据损坏或身份修改未决的记录不能进入候选。用合成星表验证新增与修订，修改摘要准确，修订前后内容和依据均能回查。

## R23

**静态星表网站与独立下载**

**目标与交付：** 生成可浏览、搜索并查看来源和修订的静态星表网站，提供程序与数据的独立下载入口。

**分工与开始条件：** GLM 实施，Astra 验收技术与内容一致性，人类专家审核呈现。开始前需完成 R22。

**关键要求：** 页面、表格和下载采用同一固定数据版本。保留多来源测量及版本导航，社区建议通过 GitHub issue/PR 提交；本关仅准备本地或获准私有预览。

**验收标准：** 在桌面与窄屏真实浏览器中检查搜索、导航、来源和下载。内容与版本一致，不误呈现唯一推荐参数；程序可独立安装，预览不会自动公开网站。

## R24

**项目与数据指南**

**目标与交付：** 为新用户制作中文指南，解释项目如何用 AI 从文献提取数据、设计原则如何影响结果，以及如何浏览、理解和使用最终星表。指南作为 R23 星表网站的一部分交付，链接来源记录、字段说明和下载入口。

**分工与开始条件：** Codex / Astra 直接设计、制作并核对技术与科学解释，人类专家验收可理解性和使用指引。开始前需完成 R23；本关在 R23 后、R25 前执行。

**关键要求：** 制作前与人类专家确定内容提纲，以及对自行安装和处理文献的讲解深度。根据已实现并验证的流程，使用合成或获准公开的例子，说明 AI、自动检查与专家裁决的作用，以及多来源测量、原文证据、版本和使用限制。内容归属与更新遵循 [文档维护规范](../CONTRIBUTING.md#文档维护与防止漂移)，页面路径和源文件组织结合实际网站确定。演示无需真实模型调用，不使用私有 Gold 或最终评价预留材料；尚未完成的功能和评价明确标注。

**验收标准：** 人类专家能沿例子说明一条数据怎样从原文进入星表，找到测量的来源、条件与版本，并完成浏览和下载。桌面与窄屏真实浏览器离线检查讲解、导航和实际采用的交互；字段、链接和示例与对应版本一致。指南纳入网站构建与后续发布检查，开发阶段交付本地或获准私有预览，最终内容在 R30 核对。

## R25

**整批确认与可恢复发布机制**

**目标与交付：** 交付整批确认与可恢复发布功能，按批准范围更新仓库、网站和下载，并记录各渠道结果。

**分工与开始条件：** Astra 设计确认、事务和恢复流程，人类专家验收；GLM 实施，Astra 验证。开始前需完成 R22、R23 和 R24。

**关键要求：** 批准对应准确候选内容和目标，数据提交只包含获准文件。重试前核对已完成部分；内容或目标变化重新确认。默认私有，远程冲突不强推覆盖，真实公开另行授权。

**验收标准：** 用模拟远程与发布服务验证内容变化、重复操作、推送失败、远程变化和部分渠道失败。重启后能继续，不重复创建版本或夹带其他文件；标记成功有实际结果依据。

## R26

**完整流程与专家工作量实验**

**目标与交付：** 用一小批获准开发材料运行完整流程，交付科学质量、专家工作量、费用及可审阅的星表和发布候选。

**分工与开始条件：** Astra 设计实验、执行和分析，人类专家验收结论；GLM 修复明确的工程问题。开始前需完成 R17–R25，并取得本次实验授权。

**关键要求：** 按 [实验安排](#验证与实验安排) 固定本轮方案及故障场景，验证获取、提取、对象关联、补全、裁决和候选生成。

**验收标准：** 达到预定质量条件，普通正常记录无需逐项批准。一篇等待裁决时其他论文可继续，重启后正确恢复；已有星表新增、修订后只改变应变内容，原有依据可查，修改摘要准确。失败、部分结果、专家时间和费用完整报告。

## R27

**最终安装验证、安装包内容与自动检查**

**目标与交付：** 交付最终独立安装验证和持续自动检查，确认代码包、必要资源及文件发行范围正确。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R26。

**关键要求：** 按 [内容归属](../docs/design.md#内容进入哪里) 检查安装包，逐项核对规则、提示、模型配置和页面资源均已包含。持续集成按 [验证要求](../CONTRIBUTING.md#验证要求) 执行离线检查，核对版本、生成说明与来源、文档链接及计划与进度的关卡对应。

**验收标准：** 在无旧仓、专用路径、Gold、密钥或网络的全新环境中，从仓库外安装构建产物，完成初始化、指定快照导入、离线示例、网页及独立子进程操作。测试隔离实际生效，支持平台和安装说明有实测依据。

## R28

**最终评价 Gold 标注、裁定与版本固定**

**目标与交付：** 为 R08 保留的独立材料完成 Gold 标注、专家裁定及获准保存，固定最终评价答案和方案。

**分工与开始条件：** Astra 制定协议、标注和复核，人类专家验收协议并裁定草稿。开始前需完成 R06、R08、R27，固定待测代码及案例的版本，并取得私库操作授权。

**关键要求：** 标注前固定待测代码、方法、模型、提示、规则、依赖和案例。使用独立标注上下文，标注者不看待测预测；用 R06 工具检查新草稿，具体内容获准后保存。

**验收标准：** 材料未用于开发，来源、证据、科学审定与保存结果可核对，答案留在私有空间。未决条目处理规则明确，不为提高分数排除难例；R29 的轮次、模型组合及通过条件在本关固定。

## R29

**对固定版本进行独立最终评价**

**目标与交付：** 对固定版本开展独立最终评价，交付分项质量、失败情况、费用和专家时间，并说明结论适用范围。

**分工与开始条件：** Astra 执行与分析，人类专家验收科学结论。开始前需完成 R28，并取得明确的实验授权。

**关键要求：** 严格使用 R28 固定的材料、答案和运行方案，分别评价自动与人工处理后的结果。若根据结果继续调参，注明材料已参与开发，并重新安排受影响验证。

**验收标准：** 实际运行与预定方案一致，失败和部分结果按规定计入分母；逐项对照科学与工程通过条件，未满足项明确阻止通过。科学结论经专家验收，不能超出小样本和实际测试范围。

## R30

**私有发布候选与最终操作说明**

**目标与交付：** 按实际系统及最终评价结果更新 README、产品设计和星表网站中的项目与数据指南，交付 docs/operations.md 操作说明及可审阅的私有发布候选。

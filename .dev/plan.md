# 项目开发计划

本计划说明怎样从零建立 hvs-catalog：每一关做什么、交付什么、如何验收。目标是建立可独立安装、维护和使用的文献提取与星表系统。产品目标、科学范围、架构和目录设计见 [产品设计](../docs/design.md)，通用开发要求见 [开发与文档维护](../CONTRIBUTING.md)。

本计划写各关目标、主要交付、依赖分工、关键要求和验收标准，[progress.md](progress.md) 记录实际进度和当前交接。实现者在明确约定下自行安排内部实现；当前已经可用的功能见 [README](../README.md)。R00 规定当前文档体系及后续维护方式。

## 开发方案

### 人员与工具分工

| 角色 | 职责 |
|---|---|
| **Zcode / GLM** | 按已审定规格实现代码、测试和配套说明，完成自检与修复。 |
| **Codex / Astra** | 负责架构与科学设计、科学任务，以及 GLM 代码的技术验收。 |
| **人类专家** | 验收架构与科学成果，决定关卡放行及提交、保存、发布等操作授权。 |

上述分工适用于本次项目建设。

### 逐关实施与交接

1. 接手的 Agent 先读 AGENTS 指定的资料、[progress 的当前交接](progress.md#当前交接)和对应任务说明。核对实际文件、Git 状态，以及本关需要的成果是否具备，再按接续安排工作。
2. 要求明确且开始条件满足时，按分工直接执行。GLM 自行安排内部文件、函数、编码顺序和测试命令，无需统一提交详细编码计划供 Astra 预审。发现影响实现或验收的具体缺口时，由 Astra 补充必要设计；主要接口和架构调整按维护规范评估，重要架构与科学选择交人类专家审定。科学任务仍须在执行前明确材料、方法、评价条件及所需授权。各关明确要求的先行设计、科学审定和实验批准继续执行。
3. 暂停、完成工作或更换 Agent 前，更新 progress 的任务行和当前交接，让接手者从文件中了解结果、问题和接下来要做什么。重要需求和设计决定写回本计划或对应文档。
4. 每次只推进当前关卡；完成验收及获准的 Git 交付后，再进入下一关。并行实施或合并关卡须经人类专家同意。

progress 包含两部分：**任务总表**每关一行，记录状态和关键结论；**当前交接**说明接手者现在需要知道什么，固定为六项：

| 项目 | 写什么 |
|---|---|
| 任务与范围 | 链接当前任务，注明涉及哪些文件。 |
| 已完成 | 写已经完成的工作及结果。 |
| 验证结果 | 写实际执行的命令、检查结果，以及哪些情况尚未验证。 |
| 待解决 | 列出未解决的问题和需要专家决定的事项。 |
| 接续安排 | 写当前由谁做什么，完成后交给谁。 |
| Git 与授权 | 写当前提交与暂存情况、已获准的操作，以及仍需批准的操作。 |

每次更新时，用当前需要的信息替换旧内容，不追加逐轮记录。更换 Agent 或从实施转入验收时，同步更新接续安排；Agent 用工具与模型标识。

保存文件后，使用同一工作目录的其他 Agent 就能读取交接并继续。换到其他工作树或机器时，先同步对应提交和必要的未提交改动，再核对实际文件与交接说明是否一致。更新交接文件本身不代表获准提交或推送。含答案的证据留在 Gold 私有空间，主仓只记录概括结论和获准资料的位置。

启动接续时，只需告知 Agent：

> 请读取 AGENTS.md、.dev/progress.md 的当前交接及对应计划，核对实际状态后执行其中的下一步；结束前更新进度与当前交接。

### 审阅与 Git

**R00 直接在会话中审阅，不制作或更新 HTML，包括本关提交/推送前的说明。** 后续关卡遵循维护规范或人类专家明确指定的审阅形式。接受成果不自动授权提交或推送。

R00 获准交付时，两仓分别建立各自的第一个提交，不继承旧的提交历史。推送目标是各仓 origin 的 main 分支。首次覆盖远程前，须由人类专家批准具体提交和覆盖范围。推送前重新核对远程最新提交，并设置保护：只有远程仍是刚核对的版本时，才允许覆盖。

后续每关分别提交和推送。仓库保持私有，是否公开由人类专家另行决定。

## 验证与实验安排

代码验证遵循维护规范。每个代码任务先用合成或获准公开的小样例，测试正常结果、失败处理和恢复。多个模块连接或打包相关的关卡，还要运行全部离线测试，在仓库外安装 wheel，并检查独立子进程能否运行。文档任务检查内容、引用和当前功能说明；网页任务还要用真实浏览器检查。

运行真实提取实验前，须先完成 R08 的 Gold 审定和 R10 的评分核对。Astra 提前确定并记录材料及来源版本、科学规则和数据格式（schema）、Gold、代码及依赖、方法、各步骤模型和参数、实际提示、所用案例、轮次、并发数、重试上限、指标、预算及停止条件。科学上的通过条件由人类专家审核后固定，不能看到结果后再修改条件来取得通过。

分别报告论文完成情况、名单精确率和召回率、候选是否找全、从名单到数值的整体正确性、证据是否对应、失败或只完成部分或尚未确定的情况、多次运行的差异、费用和专家用时。数值评价使用预定的严格要求，不能只看成功提取的字段。空预测、整篇失败和部分结果按预定规则计入分母；自动结果和人工裁决后的结果分别报告。

引用错误来源的内容进入待审正式星表、同一决定重复生效或私有答案泄露，都属于必须修复的程序问题。科学指标具体要达到多少，在相应科学任务中确定。

R18 比较两种名单方法时，使用相同的模型配置组合和其他输入，让结果差异能够用于判断方法效果。更换模型及按步骤选择模型的功能先用模拟服务验证。真实实验的论文、模型组合、重复轮次和费用在该关开工前提出并批准。

模型 API 实验总额参考 1000 RMB；单次预计可能超过 100 RMB 时先提醒并等待确认。费用估算包含步骤、轮次和重试，实际型号、协议、路由及报价在准备实验时核实；未知用量或费用保留未知。小范围运行不自动扩大为 Full50 或更多组合。

实验失败时，保留必要的原始结果，在同一评价目标下修复并重新验证；不能删除难例或失败轮次来改变结论。重新处理已有结果、假设改变某个条件的分析，以及实际调用服务的新实验，要分别标明。用于开发的材料即使经过迁移，也不能当作从未用于开发的测试材料。最终评价材料在 R09 准备并单独保存、限制访问，在 R28 标注，在 R29 独立评价。

## 任务阅读约定

共 31 关，编号为 R00–R30，每关独立实施和验收，按编号顺序逐关推进。

按上述顺序逐关推进；开始每关前，确认此前关卡已完成验收及获准的 Git 交付，并核对本关列出的依赖成果已经具备。已经确定的要求直接写在任务中；尚未确定的事项，须由任务中指定的参与者在相关工作开始前确定。

R00 审核整体方向、科学边界、模块职责、关卡顺序和成功标准。R01–R30 用“目标与交付、分工与开始条件、关键要求、验收标准”四项指导执行，不固定增加开工前细化环节，也不另建逐关任务文件。当前交接统一放在 progress，文档职责按维护规范执行。

内部函数、辅助文件、测试组织和命令参数由实现者按需要安排。科学规则、失败处理、数据使用与发布限制，以及判断成果是否合格的关键要求，应当保留。执行中发现要求不合理时，按维护规范提出调整；不能在看到结果后自行降低验收标准。

## R01

**文件架构与最小工程骨架**

**目标与交付：** 建立可以独立安装的最小 Python 包，提供命令行帮助和版本查询，以及安装与验证说明。

**分工与开始条件：** Zcode / GLM 实施，Codex / Astra 验收。开始前需完成 R00 的人类专家验收及获准 Git 交付。架构调整由 Astra 提出并交人类专家审定。

**关键要求：** 使用统一依赖管理和唯一软件版本来源。只建立当前需要的工程文件；代码安装包排除正式星表、Gold、开发材料和运行产物。

**验收标准：** 在没有旧仓、Gold、密钥和本机专用路径的全新环境中，能安装构建产物，并从仓库外及独立子进程查询帮助和版本。实际支持的平台和安装步骤写入 README。

## R02

**LangGraph 持久化与恢复演示**

**目标与交付：** 用合成材料交付一个可暂停、保存决定并在程序重启后恢复的 LangGraph 演示，说明框架进度与业务数据的分工。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R01。框架不满足要求时由 Astra 提出设计调整，交人类专家验收。

**关键要求：** 先保存结果和裁决决定，再恢复流程；同一任务只允许一个执行者。演示空间与日常空间分开。框架不适用时由 Astra 提出设计调整。

**验收标准：** 实际终止进程并重新启动，能找回待办、复用已保存结果。相同决定只生效一次，冲突决定被拒绝。用模拟服务说明“收到响应但尚未保存就退出”可能造成重复调用及计费；演示不访问网络。

## R03

## R04

**目标与交付：** 交付经人类专家审定的科学规则、程序可读取的规则材料，以及容易混淆的输入和预期结果。

**关键要求：** 明确论文与对象收录、当前贡献与引用、单个对象与群体、条件、单位、误差和缺失值、后续否定及证据要求。确定对象识别、外部资料范围、检索覆盖和自动通过或交专家的条件；提出评价目标。

**验收标准：** 规则、说明和例子一致，能避免无依据地把群体或条件结论归给单个对象。采用或修改规则有科学理由，未决问题不进入依赖它的实现。具体科学取值和阈值在本关审定，评分公式在 R10 实现前审定；科学边界遵循产品设计。

## R05

**核心数据格式与自动生成的格式说明**

**目标与交付：** 实现论文、来源包、贡献、名单、对象、外部资料、裁决和运行/发布记录，并从定义自动生成数据格式说明。

**验收标准：** 合法记录保存后读回内容不变，生成说明与定义一致。版本未知、引用损坏或对象/论文对应错误会报错；缺失、区间和特殊值按规则表达，提取失败不被记成成功空结果。

## R06

**工作空间、运行记录与裁决基础**

**目标与交付：** 交付独立工作空间、配置与运行记录、备份恢复，以及创建和查询裁决待办、保存决定的共同接口。

**验收标准：** 用模拟流程验证重复初始化、并发启动、保存中断和重启。待办、决定、论文与步骤对应正确；相同决定只生效一次，冲突或过期决定被拒绝。恢复备份后，材料、业务结果和框架进度保持一致，在仓库外也能运行。

## R07

**Gold 迁移、草稿检查与受控保存工具**

**目标与交付：** 用合成材料交付 Gold 迁移、逐项比较、草稿检查及获准保存工具，同时支持没有旧答案的全新草稿。

**分工与开始条件：** Astra 明确新旧格式的对应关系和允许进行的科学修改，人类专家验收科学含义；GLM 实现工具，Astra 验收。开始前需完成 R04–R06。

**关键要求：** 格式转换保持科学含义，差异或歧义交科学审定。正式新标注由 Astra 根据原文制作草稿、人类专家审定；工具检查来源和格式，只保存获准的准确内容。新草稿无需迁移记录。

**验收标准：** 既有答案迁移和全新草稿都能完成检查及模拟获准保存。输入损坏、版本不符、必要证据缺失、未批准或内容变化时拒绝保存；保存中断和重复操作不会留下半份答案或重复保存。回执读取失败时能先核对实际结果，旧输入始终只读。

## R08

**正式 Gold 迁移与科学审定**

**目标与交付：** 在获准范围内建立正式 Gold，保存材料清单、审定与来源依据，并准备供 R10 核对评分的固定参考预测。

**分工与开始条件：** Astra 使用 R07 已验收的工具执行迁移核查和科学复核，人类专家验收科学内容；GLM 修复已明确的工具问题并交 Astra 复验。开始前需完成 R07，并取得读取、迁移及保存 Gold 的具体授权。

**关键要求：** 先核对正式输入版本和审定依据，再逐项比较。科学修改须依据原文并由人类专家裁定；具体材料与保存内容另行批准。答案和详细分析留在 Gold 私有空间。

**验收标准：** 条目、身份、来源及科学内容能够逐项核对；含义未变的部分一致，修改有批准依据，未决项按规则保留。保存结果与批准内容一致，R10 能使用对应评价版本的参考预测。

## R09

**独立最终评价材料的准备与隔离**

**目标与交付：** 提前选出少量未用于开发的最终评价论文，交付固定清单、来源版本、选材理由和专家工作量估算。

**分工与开始条件：** Astra 选材并评估隔离条件，人类专家验收名单与工作量。开始前需完成 R04、R08，并取得材料获取授权。

**关键要求：** 核对材料是否参与过提取开发、提示或模型调整、案例积累。将选定材料单独保存并限制访问，正式标注安排在 R28。

**验收标准：** 能核查材料独立性和访问范围，已知限制明确，专家认可选材及工作量。样本规模在本关确定；开发期间不使用这些材料调试方法或配置。

## R10

**共享提取入口与独立评分基础**

**目标与交付：** 交付日常运行与评测共用的提取入口、方法与步骤约定，以及独立评分和报告功能。

**验收标准：** 程序评分与手算样例及 R08 的参考预测核对一致，评价目标变化有说明。空预测、整篇失败和部分结果按规则计入分母，费用未知保留未知；评价输入变化可被发现，运行与评分入口实际可用。

## R11

**文献发现、导入与获取**

**目标与交付：** 交付按条件发现论文、按标识获取材料和导入本地文件的能力，保存元数据及来源版本。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R04、R06、R08。数据来源和检索范围由 Astra 设计、人类专家验收。

**验收标准：** 离线验证修订、重复、缺失全文、限流、无权限和无结果的处理。在批准的小范围内实际获取材料，确认满足检索要求，能回查标识、版本与来源。

## R12

**来源包、正文与表格解析**

**目标与交付：** 交付版本固定的论文来源包，解析正文及表格，使证据对应原文位置和正确对象。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R05、R11。来源解释中的科学歧义由人类专家裁定。

**关键要求：** 保留原始材料及文件、页、表、行列位置。开工前确定支持格式和解析方法，核对来源与许可；解析结果不能替代原文依据。

**验收标准：** 检查正文与表格的证据对应，尤其是 ECSV 异常列名（如 col_001）、YAML 头、多行和同名对象。无法匹配对象时不得默认使用第一行；解析失败、引用损坏和错误对象对应被发现。PDF 等格式只声明实测能力。

## R13

**模型接口与完整配置**

**目标与交付：** 交付可配置的模型调用接口，保存实际参数、响应、用量和失败状态。

**关键要求：** 按实际协议使用模型的完整配置，核对支持的参数；不强制不同模型采用同样设置，不擅自更换模型。对技术故障限制重试次数，日志与运行记录去除密钥。

**验收标准：** 模拟验证超时、限流、错误格式、截断、空响应、未知参数及用量缺失。能区分失败和无法确认调用是否完成的情况，未公开的默认值保留未知；真实服务调用另按范围授权。

## R14

**为各步骤选择模型、组合提示并保存运行配置**

**目标与交付：** 交付默认模型与按步骤指定模型的能力，保存实际完整提示及配置，供日常运行、恢复和评测共同使用。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R13、R04，并具备 R10 定义的方法与步骤接口。

**关键要求：** 共同科学要求、方法必需提示和模型补充提示职责清楚。关闭补充提示后科学要求仍完整；更换一步模型不改变其他步骤。恢复沿用固定输入，材料、规则、方法或配置变化后不能误用旧结果。

**验收标准：** 模拟验证多步骤模型组合、逐步用量及总费用。不存在的步骤会报错，不混用不同协议参数；恢复后模型和提示正确。真实组合在实验前选定，不自动遍历付费组合。

## R15

**统一名单格式与直接提取**

**目标与交付：** 实现 direct 名单方法，按规则直接提取对象、角色和证据，输出两种方法共用的名单格式。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R04、R05、R10、R12、R14。科学质量由 R18 的真实实验检验。

**关键要求：** 使用固定来源、规则和步骤配置，保留未决项，检查证据对应。方法不得按论文标识预置答案，格式修复有次数上限。

**验收标准：** 用模拟服务和 R04 样例检查贡献与引用、单个对象与群体、条件及后续否定。失败或截断不表示成功空名单。通过 R10 模拟步骤检查后续输入要求，R17 再验证与实际数值提取的连接。

## R16

**候选发现与逐项模型判定**

**目标与交付：** 实现 candidate_review 名单方法：先发现候选，再由模型逐项判定，保存每项证据、理由和进度。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R15、R02，以及 R06 的共同裁决接口。

**关键要求：** 发现和判定都能查看原材料。每个候选得到对应结果，尚未完成的候选不能自动排除；未决项交 R06 共同裁决接口，输出与 direct 共用后续流程。

**验收标准：** 发现重复或同名候选、无效证据、单项失败及分批结果错配。进程退出后能恢复部分结果，通过共同接口保存模拟决定并继续正确候选。候选遗漏单独检查，真实论文上的覆盖由 R18 评价。

## R17

**数值提取、自动检查与部分结果保存**

**目标与交付：** 交付完整论文提取流程，连接来源、两种名单方法、共同数值提取和自动检查，并提供日常运行入口。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R15、R16。

**关键要求：** 保留数值、误差或区间、单位、条件、对象及来源。区分技术失败、科学歧义和论文确实未报告内容；有效部分结果保留。逐篇保存进度，未决问题使用 R06 接口，不阻止其他可运行论文。

**验收标准：** 两种名单方法实际进入同一数值步骤，日常运行与评测使用相同配置和服务。模拟两篇论文，一篇等待裁决时另一篇能完成；重启后结果与待办正确，已保存结果可复用，决定只恢复对应论文。文献处理、R07 的 Gold 工具和评测入口均可执行。

## R18

**首轮真实提取实验与结构问题复查**

**目标与交付：** 交付首轮小范围真实提取实验，比较两种名单方法、科学质量、失败原因和多次运行稳定性。

**分工与开始条件：** Astra 设计并执行实验、分析结果，人类专家验收科学结论；GLM 修复范围和要求已明确的代码问题。开始前需完成 R08、R10–R17，并取得本次实验授权。

**关键要求：** 运行前批准材料、模型组合、重复轮次、通过条件和预算，固定全部评价输入。比较方法时保持模型配置组合及其他输入相同；先复查已知失败情况，保留全部轮次和费用。

**验收标准：** 分别报告名单、候选覆盖、数值、证据、失败和部分结果的指标，逐项对照通过条件。修复后在同一评价目标下复验；离线重处理不冒充新实验，小范围结论不扩大到 Full50 或未测场景。

## R19

**稳定对象身份与合并拆分**

**目标与交付：** 交付跨论文对象关联、稳定身份以及合并、拆分和更正能力，保留依据与原有论文贡献。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R04、R05、R06、R18。对象关联规则及科学分歧由 Astra 分析、人类专家验收。

**关键要求：** 按 R04 规则使用标识、别名和位置提出关联建议；无法确定时通过 R06 保存待办，交专家裁决。名称相同不能直接认定为同一天体，匹配计算不得扩展为自主物理筛选。

**验收标准：** 同名不同对象保持区分，改名不改变稳定 ID；合并拆分后贡献不丢失、不重复，旧链接和引用仍可解释。根据保存记录重建得到一致结果，未决关联可回查。

## R20

**来源明确的外部资料补全**

**目标与交付：** 从审定的外部来源补充允许使用的观测、标识和质量信息，保留匹配及来源依据。

**分工与开始条件：** GLM 实施，Astra 验收。开始前需完成 R04、R19，并取得具体服务调用授权；科学字段与匹配解释由人类专家验收。

**关键要求：** 具体来源、字段和查询范围在开工前依据 R04 确定，可检查 SIMBAD 和 Gaia 等必要来源。保留查询、返回条目及版本，不覆盖论文值，不自行计算动力学或选择最佳参数。

**验收标准：** 离线验证多匹配、无匹配、来源版本变化和服务故障；在批准范围内核对少量真实条目的字段、单位与出处。调用失败不表示数据库没有该对象，匹配不确定时保留待决状态。

## R21

**本地裁决网页、CLI 与恢复**

**目标与交付：** 将 R06 的共同裁决接口接入本地网页和命令行，让专家查看证据、保存决定并恢复任务。

**分工与开始条件：** Astra 设计操作流程及允许保存的内容，人类专家验收；GLM 实施，Astra 验证。开始前需完成 R02、R06、R17、R19、R20。

**关键要求：** 两种入口使用相同记录、保存与恢复功能及执行锁；先保存决定再恢复。默认只在本机使用，页面操作不自动修改通用科学规则或公开数据。

**验收标准：** 真实浏览器验证待办与证据展示、刷新、关闭和重启。重复决定只生效一次，过期证据或规则对应的提交被拒绝，裁决后从正确步骤继续；网页和命令行行为一致，不同工作空间互不影响。

## R22

**裁决案例积累、复用与汇总**

**目标与交付：** 交付裁决案例的保存、查找、按条件复用和问题汇总，记录专家投入的时间。

**分工与开始条件：** Astra 设计复用规则并交人类专家验收，GLM 实施，Astra 验证。开始前需完成 R21。

**关键要求：** 复用条件先经科学审定，保留材料、规则、证据和原决定；相似案例可供参考，不能自动视为适用。评测使用固定案例集合，产品不自行调用开发 Agent 修改代码或启动实验。

**验收标准：** 符合条件的案例可复用，条件变化后重新检查；复用引用原批准，不生成一次虚假的新批准。新增案例不改变当前评测，重复问题、待办和专家用时能够导出查看。

## R23

**正式星表候选与数据导出**

**目标与交付：** 从工作结果生成版本明确、来源可查的星表候选和下载表格，支持在已有星表上新增论文与修订记录。

**分工与开始条件：** Astra 确定哪些结果可以入库、导出内容如何表达，人类专家验收；GLM 实现，Astra 验证。开始前需完成 R19–R22。

**关键要求：** 按专家审定的入库和导出规则准备候选。不同来源测量分别保存，不能合成推荐值；未受影响记录保留，新增和修订及受影响对象写入修改摘要。正式保存须批准准确内容。

**验收标准：** 相同输入产生相同候选内容及哈希，贡献和引用不丢失、不重复；关键证据损坏或身份修改未决的记录不能进入候选。用合成星表验证新增与修订，修改摘要准确，修订前后内容和依据均能回查。

## R24

**分工与开始条件：** GLM 实施，Astra 验收技术与内容一致性，人类专家审核呈现。开始前需完成 R23。

**关键要求：** 页面、表格和下载采用同一固定数据版本。保留多来源测量及版本导航，社区建议通过 GitHub issue/PR 提交；本关仅准备本地或获准私有预览。

**验收标准：** 在桌面与窄屏真实浏览器中检查搜索、导航、来源和下载。内容与版本一致，不误呈现唯一推荐参数；程序可独立安装，预览不会自动公开网站。

## 进度与变更维护

progress 的任务总表每关一行，使用“未开始、进行中、待审核、需修改、通过”五种状态。代码任务先由 Astra 验收，再由人类专家审核并决定是否通过；架构和科学成果由人类专家验收。只有人类专家确认通过后，才填写“通过”和验收日期。提交与推送情况查看实际 Git 状态，不在文档中手工维护当前提交 SHA。

本计划保存关卡要求及其变化；持续有效的科学与架构决定写入产品设计，内部实现和实际行为由代码与测试维护。progress 的任务总表记录实际进度，“当前交接”按前文要求填写。验证记录写实际命令、结果及限制；批准记录写具体内容和操作范围，没有明确依据就不能视为获准。

清理临时材料前，先保存接手者需要的结论和必要证据。科学实验与 Gold 材料按规定放在对应空间。主仓 `.dev/` 只固定维护这两份文件，并将它们纳入 Git。

需要修改已经审定的架构或科学含义时，由 Astra 说明为什么改、影响哪些部分、需要怎样验证，再交人类专家验收。任务交付或通过条件变化时，同时更新本计划。重要要求必须写回正式文档，让更换开发工具后的接手者仍能读到并遵循。

最终评价的输入和版本固定后，如果修改运行代码、科学规则、方法、提示、依赖或案例，需要重新完成受影响部分的验收。只整理说明文字时，不重复无关的付费实验。项目建设完成后，经人类专家确认，移除两仓 AGENTS 中的开发阶段入口；产品文档继续随实际功能更新。
